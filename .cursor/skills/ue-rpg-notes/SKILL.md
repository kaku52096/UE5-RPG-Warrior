# UE5 RPG 学习笔记

把「对照视频实现功能、在 Cursor 里追问概念」收束成给未来自己看的设计笔记。文章要说明要解决什么、系统怎么拆、每一步依赖什么概念，以及为什么这样设计。

## 何时使用

用户明确要求整理笔记 / 根据 diff 写文档时才写文件。日常答疑只讲概念，不要边问边改博客。

## 输入

按顺序收集，缺了就问一句：

1. **课次**：第几课、标题（对照 `e:\Dev\Web\my-blog\posts\UE5 RPG *.md` 已有序号）
2. **代码变化**：在 `e:\Dev\UE\Warrior` 跑 `git status`、`git diff`；若用户给了 commit/范围，用 `git diff <from>...<to>`。只看 `Source/`、`Config/`、相关蓝图路径名，忽略 Binaries/Intermediate/Saved。
3. **提问**：提取本对话里用户真正不懂、且与本课实现直接相关的问题。把答案放回对应实现环节，不要汇总成独立问答集。
4. **既有文风**：读最近 1 篇同系列文章的 frontmatter 和结构，对齐 title/slug/tags，不要复制它的实现细节。

## 写作流程

严格按下面顺序组织：

### 1. 需求分析

- 先写玩家可感知的目标，再写系统必须满足的约束。
- 给出完整输入与输出。例如：攻击动画和命中目标是输入，目标生命值变化是输出。
- 列出 3～6 个实现环节，但不要写编辑器操作步骤。

### 2. 实现拆分

- 按数据流或调用顺序拆成若干小节，每节只解决一个职责。
- 每节先说「这一层负责什么」，再说本项目用了哪些关键类型，以及数据如何流向下一层。
- 在对应小节内写 `### 概念解析：...`，解释用户在这个环节问过的问题。概念不能脱离实现单独堆放。
- 只保留理解当前设计所需的概念。与本课代码链路无关的问题不写进文章。
- 类型名只用于标明职责边界，不逐函数复述 diff。

### 3. 设计动机与取舍

- 说明为什么选择当前职责划分，而不是最直接但耦合更高的方案。
- 至少写清：当前方案得到什么、付出什么、什么情况下应换方案。
- 把用户问过的坑改写成可执行的判断标准。

## 表达要求

- 文字简单、清晰、明确。优先使用短句，一段只表达一个结论。
- 先写结论，再写原因。少用括号和长串并列。
- 同一概念只解释一次；后文直接沿用。
- 不写聊天语气，不出现“你问过”“视频里”“老师先做了”等表述。
- 不为了覆盖对话而扩写百科。文章服务于本课的实现链路。

禁止写：

- 视频操作清单（先创建 X 再创建 Y、在面板里勾哪个框）
- 完整 `.h` / `.cpp` / 蓝图节点流水账
- 逐行解释 `UPROPERTY`、include、生成代码
- 把 diff 里每个函数都讲一遍
- 先列一章“关键概念”，再列一章重复内容的“实现细节”
- 把所有提问不分主次地塞进文章

代码块最多 1～2 个、每个不超过约 15 行，只展示接口形状、数据流或关键不变量。能用一句话讲清就不贴代码。需要截图处写 `figures/ue_rpg_N/xxx.png` 占位，不要编造图片。

## 输出

写入 `e:\Dev\Web\my-blog\posts\UE5 RPG {N} {短标题}.md`。已有同课文件则改写提升抽象度，不要在文末追加实现附录。

## 完成前检查

- 只看各级标题，是否能还原完整实现链路？
- 每个概念是否紧跟它解释的实现环节？
- 是否明确区分了职责、数据和控制流？
- 是否说明了方案的收益、成本和替代条件？
- 是否删掉了与本课无关的百科知识和操作步骤？

写完后用 3 条 bullet 说明：修改了哪篇、按什么实现链路组织、删掉了哪些无关或重复内容。
